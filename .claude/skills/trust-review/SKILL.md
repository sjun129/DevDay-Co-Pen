# Trust review

검토 대상(현재 diff, 지정한 파일, 또는 설계 문구)을 아래 체크리스트로 판정하고 표로 보고한다. 근거와 원칙의 자세한 설명은 `docs/PROJECT_CONTEXT.md` 5장과 `reports/AI 협업 에디터 신뢰성 설계.md`에 있다.

## 절차

1. 대상을 확인한다. 코드라면 `git diff` 또는 지정 파일을 읽고, AI가 문서를 바꾸는 경로(워커 `run-job.ts`, `stream-writer.ts`, 웹 `ai-suggestion.ts`, 수락·거절 UI)를 추적한다.
2. 아래 항목마다 **충족 / 부분 / 위반 / 해당 없음**으로 판정하고, 위반·부분이면 파일:줄과 구체적 수정안을 적는다.
3. 발표·README 문구가 포함되면 `claim-check` 스킬 기준도 함께 적용한다.

## 체크리스트

**A. 인간 감독·가역성**
- AI 변경은 제안으로만 들어가는가? 사람 수락 없이 확정되는 경로가 없는가?
- 모든 AI 변경을 작업 단위로 되돌릴 수 있는가? 작업마다 고유 origin을 쓰고 경계에서 `stopCapturing()`을 호출하는가?
- 사람의 동시 수정이 AI 작업·되돌리기 과정에서 사라지지 않는가? (보존 검사 또는 테스트 존재 여부)
- 전역 일시정지·AI 금지 구역을 우회하는 경로가 없는가?

**B. 과의존 완화**
- 확인 절차가 위험 비례인가? (근거 없는 수치·날짜·고유명사·인용만 Tier 2) 모든 제안에 같은 확인을 걸지 않았는가?
- "모두 수락"이 Tier 2를 건너뛰는가?
- 설명 카드가 "왜"보다 원문 대조를 먼저 보여주는가?
- 숫자 신뢰도 배지, 대기 타이머, 동일 경고 모달을 쓰지 않았는가?

**C. 책임·출처**
- AI 기원 스팬에 `agent_id, role, model, prompt_id, op_type, accepted_by, accepted_at`이 남는가? 수락 뒤에도 유지되는가?
- 감사 로그가 클라이언트가 고칠 수 없는 곳(서버 전용, append-only)에 쌓이는가?
- 내역서 내보내기와 감사 로그가 일치하는가?

**D. 인젝션·안전**
- 지시는 인증된 멘션에서만 오고 문서 본문은 데이터로만 전달되는가? (L1)
- 계획의 대상·행동을 코드가 허용 집합으로 검증하는가? 실행기에 사람 원문 지시를 넘기는가? (L3)
- 출력에서 URL·이미지·HTML을 제거하고 plain text로 렌더링하는가? (L4)
- 새 외부 통신 채널(네트워크 도구, 링크 렌더링)을 열지 않았는가?

**E. 범위**
- 채점, 기여도 평가, AI 작성 탐지처럼 고위험·고영향 분류를 바꿀 수 있는 기능을 넣지 않았는가?

## 출력 형식

| 항목 | 판정 | 근거(파일:줄) | 수정안 |
|---|---|---|---|

마지막에 "가장 먼저 고칠 것" 1~3개를 적는다. 체크리스트에 없는 새 위험을 발견하면 따로 적는다.
