# Concurrency bench

## 무엇을 증명하나

- **사람 수정 보존률**: AI가 재작성하는 동안 사람이 한 수정이 최종 결과에 모두 남는가.
- **undo 정확성**: AI 작업 하나를 되돌리면 그 작업의 스팬만 사라지고 사람 스팬은 바이트 단위로 같은가.
- **앵커링 정확도**: 위쪽 편집이 있어도 AI 글이 의도한 블록 뒤에 들어가는가(기획서 목표 20/20).
- **반영 지연**: 사람 N명 + AI M개 동시 편집에서 업데이트가 다른 클라이언트에 반영되는 시간(기획서 목표 1초 이하).

## 하네스

위치는 `apps/agent-worker/eval/concurrency/` (없으면 만든다).

1. 동기화 서버와 워커를 실제로 띄운다(`npm run dev:sync`, `npm run dev:agent`).
2. 봇은 `HocuspocusProvider` + `Y.Doc`으로 접속한다(토큰 `guest`). 워커 코드의 `summarizeBlocks`, `getFragment`(`apps/agent-worker/src/doc-model.ts`)를 재사용한다.
3. 시나리오마다 새 문서 이름을 쓴다(예: `bench-<시나리오>-<반복>`). 이전 결과가 섞이지 않게 한다.
4. 사람 행동은 Y 트랜잭션으로 흉내 낸다: 오타 수정, 이름 변경, 절 추가, 문장 삭제, 위쪽 문단 삽입. 멘션은 stateless `agent:mention`(state vector 포함)으로 보낸다.
5. 최종 판정은 **서버 쪽 문서**를 별도 봇으로 읽어서 한다. 브라우저 DOM이나 한 클라이언트만 보고 판정하지 않는다.

## 비교 기준선 (semantic rebase 평가 시)

1. 단순 덮어쓰기(lost update)
2. CRDT 인터리빙(그대로 병합)
3. reconcile-text 3-way 병합
4. LLM rebase + 토큰 단위 보존 검사

합성 사례 30~50건을 사례 유형별로 나눠 보존률과 유창성(사람 평가 또는 간단한 기준)을 보고한다.

## 보고

- 지표별 표본 수, 평균·분포, 실패 사례 원문.
- 목표치는 "팀이 정한 기준"이라고 명시한다.
- 측정하지 않은 조건(네트워크 지연, 대형 문서, 한국어 이외 텍스트 등)을 적는다.
- 실패가 나오면 재현 가능한 최소 시나리오를 남기고 원인을 조사한다. 수치를 맞추려고 시나리오를 고치지 않는다.
